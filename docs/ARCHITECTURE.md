# lexFlex — Architecture

## What is lexFlex?

A **universal meaning representation framework** that uses **Interlingua** as a language-neutral semantic core. lexFlex supports multiple language types through a layered plugin architecture:

- **Natural languages** (Polish, English, German) — with morphology, syntax, pragmatics
- **Formal languages** (mathematics, logic) — with grammar, symbols, proofs (future)
- **Programming languages** (Python, SQL, Rust) — with AST, semantics, execution (future)

Each language is a **plugin** that implements the appropriate trait layer and maps to/from the universal Interlingua representation.

### Design Principles

- **Interlingua is the source of truth** — not any single language
- **Layered abstraction** — different language types expose native capabilities
- **Data-driven** — linguistic knowledge lives in data files (RON), not in code
- **Algorithmic morphology** — word forms are generated by rules, not lookup tables
- **Plugin architecture** — adding a language = adding a new engine + data files
- **Capability-based translation** — check what target can express before translating
- **Minimal resources** — Rust core, ~2-5MB binary, ~1-3MB RAM for 5 languages × 500 words

## Layered Abstraction Architecture

lexFlex uses a **layered trait hierarchy** to support different language types while maintaining a universal protocol.

```
┌─────────────────────────────────────────────────────────────┐
│                    Layer 0: Core Protocol                    │
│         IMeaningRepresentation (Universal Trait)            │
│   - to_interlingua(input) → Result<Interlingua>            │
│   - from_interlingua(il) → Result<output>                  │
│   - capabilities() → Vec<Capability>                       │
│   - limitations() → Vec<Limitation>                        │
└─────────────────────────────────────────────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
        ▼                     ▼                     ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Layer 1    │    │   Layer 2    │    │   Layer 3    │
│  INatural    │    │   IFormal    │    │ IProgramming │
│  Language    │    │   Language   │    │   Language   │
│              │    │              │    │              │
│ • parse()    │    │ • parse_expr │    │ • parse_code │
│ • generate() │    │ • render     │    │ • generate   │
│ • inflect()  │    │ • validate   │    │ • transpile  │
│ • descriptor │    │ • grammar    │    │ • AST        │
│ • lexicon    │    │ • symbols    │    │ • semantics  │

│    German    │    │              │    │     Rust     │
└──────────────┘    └──────────────┘    └──────────────┘
```

### Why Layered Abstraction?

Different language types have fundamentally different structures:

- **Natural languages** have morphology, syntax, pragmatics, discourse
- **Formal languages** have grammar, symbols, proofs, but no morphology
- **Programming languages** have AST, semantics, execution, but no pragmatics

A single `ILanguageEngine` trait would force all languages into the same mold. Layered abstraction lets each language type expose its **native capabilities** while maintaining a **universal protocol** (Interlingua) for translation.

## The Five Layers of Language (Natural Languages)

For natural languages, every utterance encodes information across five layers. **Interlingua lives on layers 3–5. Language lives on layers 1–2.**

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 5: DISCOURSE                                         │
│ Who speaks, to whom, for what purpose                      │
│ "Speaker tells addressee about a past event, neutral tone" │
│ ─── INTERLINGUA ────────────────────────────────────────── │
├─────────────────────────────────────────────────────────────┤
│ Layer 4: PRAGMATICS                                        │
│ Tone, register, intent, politeness                         │
│ "Formal request" vs "Casual statement"                     │
│ ─── INTERLINGUA ────────────────────────────────────────── │
├─────────────────────────────────────────────────────────────┤
│ Layer 3: SEMANTICS                                         │
│ Who did what to whom — predicate-argument structure        │
│ Frame::TRANSFER { agent: Tomek, recipient: Iza, theme: book}│
│ ─── INTERLINGUA ────────────────────────────────────────── │
├─────────────────────────────────────────────────────────────┤
│ Layer 2: SYNTAX                                            │
│ Sentence structure — SVO, OV, question formation           │
│ "Tomek dał Izie książkę" (PL) vs "Tomek gave Iza a book"  │
│ ─── LANGUAGE-SPECIFIC ──────────────────────────────────── │
├─────────────────────────────────────────────────────────────┤
│ Layer 1: MORPHOLOGY                                        │
│ Word forms — inflection, conjugation, declension           │
│ "Tomek" (NOM) vs "Tomkowi" (DAT) vs "książkę" (ACC)       │
│ ─── LANGUAGE-SPECIFIC ──────────────────────────────────── │
└─────────────────────────────────────────────────────────────┘
```

### Key Insight

Different languages **grammaticalize different features**. Polish encodes grammatical gender in morphology. English encodes definiteness with articles. Japanese encodes honorifics. Interlingua must have slots for ALL possible features, even if a specific language doesn't use them.

### Translation with Capability Checking

```rust
pub fn translate(
    &self,
    input: &str,
    from: LanguageId,
    to: LanguageId,
) -> Result<String, TranslateError> {
    let source = self.engines.get(&from)?;
    let target = self.engines.get(&to)?;
    
    // 1. Source → Interlingua
    let il = source.to_interlingua(input)?;
    
    // 2. Check if target can express this Interlingua
    let inexpressible = target.can_express(&il);
    if !inexpressible.is_empty() {
        return Err(TranslateError::InexpressibleInTarget {
            target: to.clone(),
            features: inexpressible,
            suggestions: self.suggest_workarounds(&inexpressible),
        });
    }
    
    // 3. Interlingua → Target
    target.from_interlingua(&il)
}
```

## Components

### Core (`src/core/`)

The language-neutral heart of the system:

- **Interlingua types** — `InterlinguaNode`, `Utterance`, `Sentence`, `Frame`, `Entity`, `SemanticRole`, `FeatureBundle`
- **Temporal reasoning** — `TemporalReference`, `TemporalResolver`, timestamp handling
- **Quantification** — `Quantifier`, `QuantifiedExpression`, scope resolution
- **Concept definitions** — what frames exist, what roles they have
- **Deduction engine** — resolves ambiguity, fills implicit information (see [DEDUCTION.md](./DEDUCTION.md))
- **Traits** — `IMeaningRepresentation`, `INaturalLanguage`, `IFormalLanguage`, `IProgrammingLanguage`
- **Capability system** — `Capability`, `Limitation`, translation validation

See: [INTERLINGUA.md](./INTERLINGUA.md)

### Language Engine (plugin) (`src/engines/<lang>/`)

Each language implements the appropriate trait layer:

**Natural languages (Layer 1):**
- **Parse** — surface string → Interlingua (with deduction)
- **Generate** — Interlingua → surface string
- **Inflect** — apply morphological rules to produce word forms
- **Descriptor** — declarative description of the language's properties

**Formal languages (Layer 2, future):**
- **Parse expression** — mathematical/logical expression → Interlingua
- **Render** — Interlingua → formatted expression (LaTeX, Unicode)
- **Validate** — syntax and semantics checking
- **Evaluate** — compute numeric results

**Programming languages (Layer 3, future):**
- **Parse code** — source code → Interlingua
- **Generate code** — Interlingua → source code
- **Transpile** — translate between programming languages
- **Format** — apply language-specific formatting

See: [ENGINE.md](./ENGINE.md), [LANGUAGE_DESCRIPTOR.md](./LANGUAGE_DESCRIPTOR.md)

### Data (`data/`)

All linguistic knowledge lives here:

- `concepts/` — master Interlingua concept definitions (~500)
- `lexicons/<lang>/` — per-language word entries mapping to concepts
- `morphology/<lang>/` — paradigm rules (algorithmic, not tables)
- `descriptors/` — declarative language descriptions
- `ontology/` — concept hierarchies and semantic relations
- `grammar/<lang>/` — formal grammars (future: math, programming)
- `symbols/<lang>/` — symbol tables (future: math, logic)

See: [LEXICON.md](./LEXICON.md), [MORPHOLOGY.md](./MORPHOLOGY.md), [ONTOLOGY.md](./ONTOLOGY.md)

## Data Format: RON

All data files use **RON (Rusty Object Notation)** — a serialization format that maps 1:1 to Rust types.

### Why RON over YAML/JSON

| Need | RON | YAML | JSON |
|------|-----|------|------|
| Rust enum variants | ✅ `Transfer { agent: ... }` | ❌ string tag | ❌ string tag |
| Option types | ✅ `Some("x")`, `None` | ⚠️ `null` ambiguity | ⚠️ `null` ambiguity |
| Type checking | ✅ via serde derive | ❌ runtime | ❌ runtime |
| Comments | ✅ `//` and `/* */` | ✅ `#` | ❌ |
| Rust struct mapping | ✅ 1:1 native | ⚠️ conversion | ⚠️ conversion |

RON is the serialization format. **Rust types are the model.** The compiler enforces data correctness.

## Advanced Features

### Temporal Reasoning

Natural languages express time through tense, aspect, and temporal adverbs. Interlingua captures all temporal information:

- **Absolute time** — "2024-01-15", "Monday"
- **Relative time** — "yesterday", "in 3 days"
- **Deictic time** — "now", "then" (context-dependent)
- **Duration** — "for 2 hours"
- **Frequency** — "every day", "twice a week"
- **Sequence** — "before X", "after Y"

See: [TEMPORAL.md](./TEMPORAL.md)

### Quantification

Natural languages express quantity and scope through quantifiers:

- **Universal** — "all", "every", "each" (∀)
- **Existential** — "some", "a" (∃)
- **Negated existential** — "none", "no" (¬∃)
- **Numerical** — "three", "five"
- **Proportional** — "most", "many", "few"

See: [QUANTIFICATION.md](./QUANTIFICATION.md)

### Discourse Management

Context that spans multiple utterances:

- **Reference resolution** — "jej" → resolved to specific entity
- **Salience tracking** — which entities are most prominent
- **Pro-drop logic** — when to omit subject (Polish)
- **Topic continuity** — what the conversation is about

See: [DISCOURSE.md](./DISCOURSE.md)

### Ontology

Hierarchical organization of concepts:

- **IS_A relations** — APPLE IS_A FRUIT IS_A FOOD
- **PART_OF relations** — WHEEL PART_OF CAR
- **Type constraints** — only ANIMATE can be Agent of EAT
- **Feature inheritance** — concepts inherit from ancestors

See: [ONTOLOGY.md](./ONTOLOGY.md)

### Speech Acts and Intents (Future)

For conversational AI:

- **Speech act recognition** — question vs request vs command
- **Intent extraction** — what the user wants to achieve
- **Emotion recognition** — sentiment analysis

See: [SPEECH_ACTS.md](./SPEECH_ACTS.md), [INTENTS.md](./INTENTS.md)

### Dialogue Management (Future)

For multi-turn conversations:

- **Dialogue state tracking** — current state of conversation
- **Response planning** — what to say next
- **Clarification strategy** — when to ask for clarification
- **Long-term memory** — user profile, preferences, history

See: [DIALOGUE.md](./DIALOGUE.md), [RESPONSE_PLANNING.md](./RESPONSE_PLANNING.md), [MEMORY.md](./MEMORY.md)

## MVP Scope

### In Scope (v0.1)

- **Natural languages**: Polish ↔ English
- **Simple sentences**: SVO structure, single or coordinated clauses
- **Parts of speech**: nouns, verbs, adjectives, pronouns, prepositions, conjunctions
- **PL features**: 7 cases (algorithmic declension), 5 genders, verb aspect pairs, agreement
- **EN features**: articles (a/the), SVO word order, tense/aspect mapping
- **Negation**: "Tomek nie dał jabłka Izie"
- **Basic questions**: yes/no ("Czy...?") and wh-questions ("Co...?", "Komu...?")
- **Coordination**: "a", "i", "ale" / "and", "but"
- **Pronouns**: personal, possessive, reflexive
- **Pronoun resolution**: within single sentence (basic)
- **Temporal reasoning**: "wczoraj", "jutro", "za godzinę"
- **Quantification**: "wszyscy", "niektórzy", "żaden"

### Out of Scope (Feature - v0.2+)

- **Conversation/chat features:**
  - Multi-turn conversation state
  - Speech act recognition
  - Intent extraction
  - Dialogue management
  - Long-term memory
  - Response planning
  - Multi-sentence coreference resolution
  - Discourse context management

- **Advanced linguistics:**
  - Complex/subordinate clauses
  - Passive voice
  - Reported speech
  - Subjunctive/conditional mood
  - Idioms and figurative language

- **Other language types:**
  - Formal languages (mathematics, logic)
  - Programming languages (Python, SQL)

- **Other:**
  - LLM-based disambiguation (rule-based for now)

```
→ EN: "For every real number x, the square of x is greater than or equal to zero"
```

### Programming → Natural (Future)

```
Python: "for i in range(10): print(i)"
→ Interlingua: Loop { For, i, range(10), [Print(i)] }
→ PL: "Powtórz 10 razy, wypisując licznik"
→ EN: "Repeat 10 times, printing the counter"
```

### Natural → Formal (Future)

```
EN: "The sum of two and three equals five"
→ Interlingua: Equation { lhs: Sum(2, 3), rhs: 5, relation: Equals }
→ Math: "2 + 3 = 5"
```

## Linguistic Graph Layer

Parsed sentences carry a **directed multi-layer graph** (`LinguisticGraph` in `src/core/graph.rs`) alongside classic Interlingua structs:

| Layer | Nodes | Key edges |
|-------|-------|-----------|
| Surface | `WordNode` | `Next`, `Prev` |
| Syntactic | `PhraseNode` (NP/PP/VP) | `SyntacticHead`, `Dependent` |
| Semantic | `EntityNode`, `FrameNode` | `Realizes`, `HasRole(role)` |
| Lexical | `ConceptNode` | `EvokesConcept`, `ConceptRelation` |
| Discourse | focus/recent via `Discourse` | `Corefers`, `NextSentence`, `InFocus` |

**Query API**: `next_word`, `find_accompaniment_paths`, `PathBuilder`, `find_coordination_for_entity`.

**Context**: `src/core/context.rs` tracks coreference and recent mentions within multi-sentence utterances; `DialogueGraph` links cross-utterance entities.

**Traces**: benchmark exports `LINGUISTIC GRAPH` RON snapshots; generation `TraceStep` records `involved_nodes` / `involved_edges`.

The graph augments IL — Interlingua RON serialization remains the stable semantic API. Graph materialization always reflects the **final** IL frame (including post-parse adjustments such as age idioms).

## Summary

lexFlex is a **universal meaning representation framework** that:

1. **Abstracts meaning** across language types (natural, formal, programming)
2. **Uses layered traits** to support different language capabilities
3. **Validates translation** through capability checking
4. **Remains extensible** — adding a new language type = adding a new trait layer
5. **Scales gracefully** — from simple PL↔EN translation to math↔code transpilation

The architecture is designed for **today's needs** (natural language translation) while being **ready for tomorrow's** (formal languages, programming languages, conversational AI).
